# 1.1 Tenant Onboarding — arquitectura (DEV)

## Lambdas

| Nombre AWS | Responsabilidad | Expuesto en API |
| --- | --- | --- |
| `mastererp-dev-db-migrator` | Aplica scripts SQL versionados (sin endpoint público) | No |
| `mastererp-dev-onboarding-session-manager` | CRUD y cierre de sesiones de onboarding | Sí |
| `mastererp-dev-onboarding-progress-tracker` | Progreso y respuestas por paso | Sí |
| `mastererp-dev-tenant-creator` | Alta idempotente de tenant + vínculo owner | Sí (POST `/v1/tenants`, política restringida) |
| `mastererp-dev-tenant-config-manager` | Lectura/actualización de configuración | Sí |
| `mastererp-dev-module-catalog-reader` | Catálogo global de módulos | Sí |
| `mastererp-dev-tenant-module-manager` | Asignación y estado de módulos por tenant | Sí |
| `mastererp-dev-onboarding-provisioner` | Activación idempotente (interno) | No |

## API Gateway HTTP

- **Nombre:** `mastererp-dev-admin-api`
- **Auth:** JWT Cognito (issuer + audience)
- **CORS:** orígenes configurables (`AllowedOrigins`)
- **Throttling:** 50 rps / burst 100 (plantilla SAM)

Rutas: ver `api/admin-onboarding-openapi.yaml`.

## Multi-tenant

- Una sola base PostgreSQL compartida.
- Aislamiento por `tenant_id` + RLS (`schema/004_tenant_security.sql`).
- Contexto de sesión: `app.current_user_id`, `app.current_tenant_id` vía `set_config(..., true)` en cada transacción.
- Alta inicial: función `SECURITY DEFINER` `plataforma.create_tenant_with_owner`.
- El backend resuelve tenant desde membresías (`user_tenants`), no desde el frontend.

## Flujo de onboarding

1. Autenticación JWT → usuario de plataforma.
2. Autorización explícita para crear tenant (`tenant.register` o `platform.admin`, o flag controlado).
3. `POST /v1/tenants` → tenant en estado `draft` + rol owner.
4. `POST /v1/onboarding/sessions` → sesión vinculada al tenant.
5. Progreso (`PUT` steps) y selección de módulos.
6. Configuración (`PATCH /v1/tenants/{id}/config`).
7. Invocación interna de `onboarding-provisioner` → módulos `active`, tenant `active`.

Step Functions: **fase posterior**; el provisioner actual es idempotente en una sola Lambda.

## Uonify (documentación, sin despliegue)

- Segundo API: `uonify-dev-api` (futuro).
- Uonify invocará las mismas operaciones de negocio vía contrato MCP/HTTP interno, reutilizando `tenant_onboarding.services.*`.
- Sin duplicar SQL ni Lambdas de dominio.

## Variables de entorno

| Variable | Uso |
| --- | --- |
| `DATABASE_HOST`, `DATABASE_NAME`, `DATABASE_SECRET_ARN` | RDS + Secrets Manager |
| `DATABASE_SSLMODE` | `require` |
| `COGNITO_USER_POOL_ID`, `COGNITO_APP_CLIENT_ID` | JWT |
| `ALLOW_TENANT_SELF_REGISTRATION` | `false` en DEV por defecto |
| `AUTH_MODE` | `cognito` (prod) / `local` (tests) |
